1. Summary

We test the SalesHiker Android app with one automated framework. It drives the real app on a real phone the way a user would (taps, typing, scrolling), checks what the screen shows, and records evidence (screenshots, UI hierarchy, device logs) for every key step and every failure.

What the framework gives the team

  • Readable tests: every test has an ID (e.g. MCMP-012) and a plain title, so anyone can read what is covered and run exactly that test.
  • Defects the team can act on: each defect has steps to reproduce, expected and actual result, severity and screenshots, kept in the Excel defect tracker.
  • Automatic records: after every run, results go into the test-case workbook, failures without a defect go to a triage sheet, defect status moves when its guard test changes, and this document is rebuilt.
  • Safe on a live workspace: real WhatsApp messages reach only 2 allowlisted test numbers, only when switched on, and the recipients are checked before and after sending.

3. How it works

3.1 From a new module to tested coverage

1 Exploreread-only walk-through on the phone (UI dumps, screenshots)
2 Page classesone class per screen; selectors from the live app
3 Specstests with IDs; smoke or regression
4 Run on devicereal phone over USB; one session per spec
5 Report keptsummary, Allure HTML, screenshots, logs per run
6 Triagetest issue, environment problem or app defect
7 Defect loggedsteps, expected / actual, severity; guard test linked
8 Records updatedworkbooks and this document rebuilt automatically

Figure 2 - Testing workflow. A failure first goes to the "Failures to triage" sheet; it becomes a defect only after triage. A test problem is fixed and re-run instead.

3.2 Defect lifecycle

1 Test failslisted under "Failures to triage"
2 Triagetest-side, environment or application defect
3 Loggeddefect with ID, severity, steps and evidence
4 Guard testthe test that fails while the defect exists
5 Developer fixesnext build of the app
6 Guard passesstatus moves to Ready for Retest
7 Retest and closeclosing is always manual
8 Reopenedautomatically, if the guard fails again

Figure 3 - A guard test keeps failing while its defect is open (its assertions describe the correct behaviour and are never relaxed). When it passes, the tracker moves the defect to Ready for Retest; "Needs Decision" and "Won't Fix" are never changed automatically.

3.3 What happens in one run

  1. Checks: the runner confirms the phone is connected and the app is installed, and records its version.
  2. Session: WebdriverIO starts Appium; the UiAutomator2 helper already on the phone is reused (ColorOS blocks reinstalls behind a security prompt).
  3. Each test restarts the app; signed-in tests sign in only when the session is gone. Tests that need data the account lacks are skipped with a reason, never passed.
  4. Safety: sending needs BROADCAST_SEND=true; the audience and recipients are checked against the allowlist; nothing is deleted.
  5. Evidence: screenshots at key steps; on failure the screen, UI hierarchy, foreground app and logcat are saved.
  6. After the run: environment aborts are reported as "not executed" (not failed), then the test-case workbook, defect tracker and this document are updated.

4. What we test, and how we keep the workspace safe

4.1 Kinds of tests

KindWhat it meansTests
smokeThe essentials of each module (test/specs/smoke); run first5
regressionFull behaviour per module (test/specs/regression)68
needs accountNeeds the beta test account from config\.env; skipped when it is missing56
expected to failGuard tests of open defects: fail until the defect is fixed7
sends WhatsAppCreates and sends a real broadcast (allowlisted numbers only); stops before sending unless switched on1
data dependentSkipped with a reason when the account has no matching data (e.g. no campaign with replies)10

Tests run by module with -Grep <prefix> (MBRD MCMP MINB MLGN REG-NAV) or one by one with its ID. There are no accessibility, performance, API, iOS or visual-comparison tests: not covered.

4.2 Safety rules on the live workspace

RuleHow it is enforced
Beta backend onlyThe APK under test points to accountsbeta.saleshiker.com; production is never used.
Real messages only to test numbersThe broadcast audience is a tag carried only by the 2 allowlisted contacts. Before sending, each number must have exactly one contact with that tag; after sending, the recipients must be exactly the allowlist.
Sending needs a switchBROADCAST_SEND=true must be set; otherwise the send test runs every check and stops before "Send Now" (skipped).
Send once, never retry"Send Now" is tapped once; "All contacts" can never be chosen by the automation.
No half-made broadcastsEvery wizard test ends with Cancel / Discard; a safety net discards an open wizard after each test.
Read-only elsewhereCampaign tests never create, pause or edit campaigns; nothing is deleted.
No secrets in gitCredentials, device serial and allowlist live in config\.env (git-ignored); the runner removes the password from all reports.

Conventions

  • Test IDs are <MODULE>-nnn (MBRD-nnn, MCMP-nnn, MINB-nnn, MLGN-nnn, REG-NAV-nnn); defect IDs are <MODULE>-Dnn (e.g. MCMP-D02).
  • Selectors and expected texts live only in the page classes; the app has no test IDs, so accessibility labels are used.
  • Test data uses recognisable names (QA_Mobile_BC_, QA_Mobile_Draft_, qa_mobile_bc_allowlist_2026) so it is never confused with real records.
